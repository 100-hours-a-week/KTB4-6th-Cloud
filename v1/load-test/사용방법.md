## 이번 테스트: 회의 생성 → 회의 참여 → 회의 진행(녹음 → 종료 → 요약·전사 조회) (15 · 20 · 50 · 100팀)

팀당 6명 기준이며, **회의 생성**, **회의 참여**, **회의 진행**을 각각 k6로 측정하고 k6 Web Dashboard 형식의 HTML 보고서를 저장합니다. 회의 진행은 팀원 전원 SSE 연결 → 녹음 시작 → 오디오 송신과 전사 수신 → 녹음 종료 → 수신 결과 검증 → 요약 완료 대기 → 팀원 전원 전사·요약 조회까지 한 번 진행합니다. 규모별로 아래 6단계를 개별 명령으로 실행합니다. 각 규모는 **새 계정과 새 팀**을 사용하므로 네 규모를 모두 실행하면 총 185팀이 생성됩니다.

| 팀 수 | 생성 계정 | k6 회의 생성 요청 | k6 회의 참여 요청 | k6 회의 진행(동시 회의) | k6 HTML 보고서 |
| --- | --- | --- | --- | --- | --- |
| 15 | 90 | 15 | 90 | 15 | `create-15.html`, `join-15.html`, `flow-15.html` |
| 20 | 120 | 20 | 120 | 20 | `create-20.html`, `join-20.html`, `flow-20.html` |
| 50 | 300 | 50 | 300 | 50 | `create-50.html`, `join-50.html`, `flow-50.html` |
| 100 | 600 | 100 | 600 | 100 | `create-100.html`, `join-100.html`, `flow-100.html` |

**측정 결과로 볼 수 있는 파일은 `create-N.html`, `join-N.html`, `flow-N.html`뿐입니다.** 각 파일은 아래 결과 디렉터리 규칙에 따라 테스트별 디렉터리에 저장됩니다. 1·2·4단계(회원·팀·fixture 준비)는 k6 밖의 순차 작업입니다. `prepare-*.html`과 예전에 만든 `prepare-20.html`, `prepare-50.html`, `prepare-50.failed.html`은 준비 건수 기록이며 부하 측정 결과가 아닙니다. 예전의 `fixtures-20.json`, `fixtures-50.json`은 참여용 회의를 미리 만든 방식이므로 사용하지 않습니다.

### 흐름

1. `prepare-teams.py`: 회원 가입·팀 생성·팀 가입 (순차 준비)
2. `prepare-meetings.py --scenarios create`: 재로그인 후 회의 생성 요청 fixture 작성 (회의는 만들지 않음)
3. **k6 회의 생성**: 팀마다 1건 동시 요청, 응답의 `meetingId`를 로그에 기록
4. `prepare-join-from-k6.py`: 3단계 로그의 `meetingId`로 회의 참여 fixture 작성 (순차 준비)
5. **k6 회의 참여**: 팀원 전원이 3단계에서 만든 회의에 동시 참여
6. **k6 회의 진행**: 팀원 전원의 SSE 연결을 확인한 뒤 팀장이 녹음 시작 → 오디오 송신(WebSocket) → 녹음 종료. 참여자는 회의 중 전사를 수신하고, 종료 후 수신 내용과 저장 결과를 검증합니다. 이어 요약 완료 후 전사·요약을 조회합니다.

### 공통 준비

작업 공간 루트에서 이동한 뒤 실제 테스트 대상 주소를 설정합니다. 이 터미널에서 이후 명령을 이어서 실행하세요.

```bash
cd project/KTB4-6th-Cloud/v1/load-test
mkdir -p reports   # 테스트별 하위 디렉터리는 각 단계 블록에서 만든다
API_URL=https://api-dev.meety.io.kr
```

- `ALLOW_LIVE_TEST=YES`는 대상 주소와 테스트 시간대를 확인했다는 표시입니다.
- `K6_WEB_DASHBOARD_PERIOD=1s`와 요청 후 VU 유지(`REPORT_HOLD_SECONDS`, 기본 8초)는 HTML 보고서를 만들기 위한 설정입니다. 짧은 테스트는 기본 설정에서 `The test run was short, report generation was skipped` 경고와 함께 HTML이 생성되지 않습니다. 대기 시간은 응답 시간 지표에 포함되지 않습니다.
- 2·4단계 출력 파일에는 계정 비밀번호 또는 토큰이 들어 있으니 공유하지 마세요. 이미 있는 출력·보고서 경로에는 저장하지 않으므로 재실행하려면 새 파일명을 사용합니다.
- **결과 디렉터리 규칙:** 결과는 테스트별로 `reports/mm-dd-hh_N팀_테스트명/`에 저장합니다. `mm-dd-hh`는 그 테스트를 시작한 시각(월-일-시)이며, 테스트명은 `create`(1~3단계), `join`(4~5단계), `flow`(6단계)입니다. 예: `reports/10-06-15_50팀_create/`. 각 단계 블록 맨 앞에서 `CREATE_DIR`, `JOIN_DIR`, `FLOW_DIR`을 정하므로 **같은 터미널에서 순서대로** 실행해야 뒤 단계가 앞 단계 파일을 찾습니다. 터미널을 새로 열었다면 세 변수를 기존 디렉터리 경로로 다시 지정합니다.
- 같은 시간대(같은 시)에 같은 규모를 다시 시작하면 디렉터리 이름이 같아지고, 준비 스크립트가 기존 파일을 덮어쓰지 않아 중단됩니다. 이때는 디렉터리 이름 끝에 `-2` 등을 붙여 변수를 직접 지정합니다.
- 4단계를 끝낸 뒤 출력되는 "가장 이른 토큰 만료" 시각 전에 5단계를 실행하세요. 2단계 토큰은 3단계 실행에 쓰이므로 그 전에 만료되지 않게 연속으로 진행합니다.
- 6단계는 1단계 계정 파일로 로그인하며, 긴 녹음 뒤 종료 요청과 요약 대기·참여자 검증 전에 필요하면 재로그인합니다. 다만 5단계 직후(참여한 회의가 아직 대기 상태일 때) 실행합니다.

#### 6단계(회의 진행) 추가 준비

**SSE 포함 k6와 로컬 조율 서버가 필요합니다.** 설치된 일반 k6의 자동 확장 해석이 `unknown dependency: k6/x/sse`로 실패할 수 있으므로 확장을 포함해 빌드합니다. 현재 macOS Apple Silicon용 `./k6-sse`는 로컬 검증용으로 준비되어 있습니다(커밋 제외). 다른 부하 발생기에서는 Go와 xk6를 설치한 뒤 한 번 빌드합니다.

```bash
# 기존 k6 설치를 교체하지 않고 현재 디렉터리에 별도 실행 파일을 만든다.
xk6 build v2.1.0 --with github.com/phymbert/xk6-sse@v0.2.0 --output k6-sse

# 별도 터미널에서 실행하고 6단계가 끝날 때까지 유지한다. Ctrl+C로 종료한다.
python3 meeting-flow-coordinator.py
```

조율 서버는 `127.0.0.1:8787`에서만 수신하며, 참여자 준비·검증 성공 여부만 저장합니다. 계정·토큰·전사 본문은 보내지 않습니다. 포트를 바꾸면 서버의 `--port`와 k6의 `COORDINATION_URL`을 함께 바꿉니다. 이 흐름은 k6와 조율 서버가 같은 컴퓨터에서 실행되는 구성을 지원합니다.


**AI가 가짜 공급자인지 먼저 확인하세요.** 실제 공급자(Speechmatics·OpenRouter·Modal)로 실행하면 팀 수만큼 요금이 부과됩니다. dev AI 서버의 `v1/dev/ai/.env`에 아래 값이 있어야 하며, 바꿨다면 `docker compose up -d`로 다시 띄웁니다.

```bash
AI_ENVIRONMENT=staging
AI_LIVE_APP=meety_ai.fake_providers:create_live_app
AI_ANALYSIS_APP=meety_ai.fake_providers:create_analysis_app
FAKE_STT_LATENCY_MS=3000          # 전사 1건 지연
FAKE_SUMMARY_LATENCY_MS=15500     # 요약 1건 지연
FAKE_DIARIZATION_LATENCY_MS=7000  # 화자 분리 지연
```

가짜 STT도 오디오를 ffmpeg로 디코딩해 **1초 분량마다 전사 1건**을 만들므로 실제 압축 오디오 파일이 필요합니다. 빈 파일이나 임의 바이트는 디코딩에 실패해 전사가 0건이 되고, 전사가 없으면 요약이 `TRANSCRIPT_EMPTY`로 실패합니다. 아래 명령으로 60초짜리 WebM/Opus 파일을 한 번 만들어 둡니다 (`audio.local.*`은 커밋되지 않습니다).

```bash
brew install ffmpeg   # 없을 때만
ffmpeg -f lavfi -i "sine=frequency=440:duration=60" -ac 1 -ar 48000 -c:a libopus -b:a 32k audio.local.webm
AUDIO_MS=60000        # 위 파일의 실제 길이(ms). 다른 파일을 쓰면 그 길이로 바꿉니다
```

- 요약은 BE 스케줄러가 5초마다 최대 5건씩 **순서대로** 처리하고 가짜 요약 1건에 15.5초가 걸리므로, 마지막 팀의 요약은 대략 `팀 수 × 16초` 뒤에 끝납니다 (15팀 약 4분, 20팀 약 5분, 50팀 약 14분, 100팀 약 27분). 이 대기 시간은 `meety_summary_ready_ms` 지표로 따로 기록되며, 대기 상한은 `SUMMARY_WAIT_SECONDS`(기본 1800초)입니다. 100팀은 여유를 두어 2400초로 실행합니다.
- 녹음 파일 업로드(S3)는 이 흐름에 포함하지 않습니다. 그래서 화자 분리 요청은 오디오 파일을 기다리다 `AUDIO_FILE_MISSING`으로 끝나며, 요약·전사 조회 결과에는 영향이 없습니다.

### 15팀 (90명)

```bash
# 1~3단계(회의 생성) 결과 디렉터리: 1단계 시작 시각 기준
CREATE_DIR="reports/$(date +%m-%d-%H)_15팀_create"; mkdir -p "$CREATE_DIR"

# 1. 회원 생성·팀 생성·팀 가입
python3 prepare-teams.py --base-url "$API_URL" --teams 15 --members-per-team 6 --output "$CREATE_DIR/teams-15.credentials.json"

# 2. 회의 생성 요청 fixture 작성
python3 prepare-meetings.py --base-url "$API_URL" --input "$CREATE_DIR/teams-15.credentials.json" --output "$CREATE_DIR/fixtures-15-create.json" --scenarios create --report-html "$CREATE_DIR/prepare-15-create.html"

# 3. k6 회의 생성: 동시 요청 15건, meetingId 로그와 HTML 보고서 저장
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_PERIOD=1s K6_WEB_DASHBOARD_EXPORT="$CREATE_DIR/create-15.html" \
k6 run --console-output "$CREATE_DIR/create-15.meetings.log" \
  -e BASE_URL="$API_URL" -e ALLOW_LIVE_TEST=YES -e FIXTURE_FILE="$CREATE_DIR/fixtures-15-create.json" \
  -e SCENARIO=create -e COUNT=15 -e CAPTURE_MEETING_IDS=YES api.js

# 4~5단계(회의 참여) 결과 디렉터리: 4단계 시작 시각 기준
JOIN_DIR="reports/$(date +%m-%d-%H)_15팀_join"; mkdir -p "$JOIN_DIR"

# 4. 생성된 meetingId로 회의 참여 fixture 작성
python3 prepare-join-from-k6.py --base-url "$API_URL" --input "$CREATE_DIR/teams-15.credentials.json" --meeting-log "$CREATE_DIR/create-15.meetings.log" --output "$JOIN_DIR/fixtures-15-join.json"

# 5. k6 회의 참여: 동시 요청 90건, HTML 보고서 저장
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_PERIOD=1s K6_WEB_DASHBOARD_EXPORT="$JOIN_DIR/join-15.html" \
k6 run -e BASE_URL="$API_URL" -e ALLOW_LIVE_TEST=YES -e FIXTURE_FILE="$JOIN_DIR/fixtures-15-join.json" \
  -e SCENARIO=join -e COUNT=90 api.js

# 6단계(회의 진행) 결과 디렉터리: 6단계 시작 시각 기준
FLOW_DIR="reports/$(date +%m-%d-%H)_15팀_flow"; mkdir -p "$FLOW_DIR"

# 6. k6 회의 진행: 동시 회의 15건(녹음 시작 → 오디오 송신 → 종료 → 요약 대기 → 팀원 90명 전사·요약 조회), HTML 보고서 저장
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_PERIOD=1s K6_WEB_DASHBOARD_EXPORT="$FLOW_DIR/flow-15.html" \
./k6-sse run --console-output "$FLOW_DIR/flow-15.log" \
  -e BASE_URL="$API_URL" -e ALLOW_LIVE_TEST=YES -e CREDENTIALS_FILE="$CREATE_DIR/teams-15.credentials.json" \
  -e FIXTURE_FILE="$JOIN_DIR/fixtures-15-join.json" -e COUNT=15 -e AUDIO_FILE=audio.local.webm -e AUDIO_DURATION_MS="$AUDIO_MS" meeting-flow.js
```

### 실패했을 때

- 1단계가 실패하면 출력 파일에서 생성된 계정·팀을 확인합니다. 자동 재시도하지 않으며, 새 파일로 다시 시작합니다.
- 3단계에서 일부 요청이 실패하면 4단계는 "회의 생성 성공 로그가 부족합니다"로 중단되어 fixture를 완성하지 않습니다. 이미 생성된 회의는 서버에 남아 있으니 같은 팀으로 3단계를 다시 실행하지 말고, 새 팀(1단계)부터 다시 준비합니다.
- 4단계가 중간에 실패하면 출력 fixture는 `preparation.complete=false`로 남으며 k6가 읽기를 거부합니다. API를 다시 호출하기 전에 원인을 확인하세요.
- 같은 fixture로 생성·참여를 반복하면 이미 만들어진 회의나 참여 기록 때문에 결과가 달라집니다. 재측정에는 새 팀 파일, 새 fixture, 새 HTML 파일명을 사용합니다.
- 6단계가 끝난 회의는 `COMPLETED`라서 다시 녹음을 시작할 수 없습니다(팀당 크레딧도 녹음 1회분 차감). 6단계를 다시 측정하려면 1단계부터 새로 준비합니다.
- 6단계의 실패 팀과 단계는 `reports/mm-dd-hh_N팀_flow/flow-N.log`의 `MEETY_FLOW_FAILED teamId=… meetingId=… step=… status=…` 줄로 확인합니다. 요약이 `FAILED`로 끝나면 `MEETY_FLOW_SUMMARY_FAILED … reason=…`이 남습니다. `reason=TRANSCRIPT_EMPTY`면 오디오 파일이나 AI 실시간 연결을, `step=summary_wait status=404`면 대기 상한(`SUMMARY_WAIT_SECONDS`)을 먼저 확인하세요.

## 파일별 역할과 옵션

### `prepare-teams.py`

회원가입, 팀 생성, 나머지 회원의 팀 가입을 **순차적으로 준비**합니다. `--teams`는 1~100, `--members-per-team`은 1~10입니다. `--delay-ms`의 기본값은 요청 사이 100ms입니다. 출력 파일에는 비밀번호가 들어가며, 기존 출력 파일을 덮어쓰지 않습니다.

### `prepare-meetings.py`

준비된 계정을 다시 로그인하고 k6 fixture를 만듭니다. 이번 흐름에서는 `--scenarios create`를 사용하며, 회의를 서버에 만들지 않고 회의 생성 요청 정보만 기록합니다. (`create-join`·`join`은 참여용 회의를 미리 생성하는 방식이라 이번 흐름에서 쓰지 않습니다.) `--report-html`은 준비 건수만 HTML로 저장하며 실패·중단 시 별도 `.failed.html`을 남깁니다. `--report-only`는 기존 fixture로 HTML만 만들고 API를 호출하지 않습니다.

### `prepare-join-from-k6.py`

회의 생성 k6의 `--console-output` 로그에서 `MEETY_CREATED_MEETING teamId=… meetingId=…` 줄을 읽어 회의 참여 fixture를 만듭니다. 모든 팀의 성공 로그가 정확히 하나씩 있어야 하며, 각 `meetingId`는 해당 팀의 회의 목록 조회(읽기 전용)로 확인합니다. 팀원마다 다시 로그인해 `POST /api/v1/meetings/{meetingId}/participants` 요청 정보를 기록합니다. 로그에 응답 전체나 토큰은 남지 않습니다.

### `api.js`

`SCENARIO=create`는 회의 생성, `SCENARIO=join`은 회의 참여입니다. `COUNT`가 동시 실행할 VU 수이며 **VU당 요청을 1번** 보냅니다. `CAPTURE_MEETING_IDS=YES`는 `create`에서만 사용하며 성공 응답의 `meetingId`를 로그에 기록합니다. `REPORT_HOLD_SECONDS`(0~60, 기본 8)는 요청 후 VU를 유지해 Web Dashboard HTML이 생성되게 합니다.

### `meeting-flow.js`

회의 진행(6단계) 시험입니다. `meeting_flow` 시나리오는 팀당 녹음 VU 1개, `meeting_participants`는 참여자당 SSE VU 1개를 실행합니다. 팀당 6명이면 **15팀은 녹음 VU 15개 + SSE VU 90개**, 100팀은 100개 + 600개입니다. 같은 회의 ID를 사용하며 모든 참여자의 `CONNECTED` 확인 뒤 그 팀의 녹음을 시작합니다.

| 순서 | 동작 | 지표 `operation` 태그 | 성공 기준 |
| --- | --- | --- | --- |
| 1 | 팀장·참여자 로그인 | `login` | 200 + `accessToken` |
| 2 | 팀원 전원 SSE 연결 | `sse_ready` | 제한 시간 안에 전원 `CONNECTED` 확인 |
| 3 | 녹음 시작 | `recording_start` | 201 + `recordingSessionId` |
| 4 | 오디오 WS 송신 + 전사 SSE 수신 | `ws_audio`, `sse` | 전체 송신, 조기 단절·오류 없음, 시작·종료 이벤트와 최소 전사 수신 |
| 5 | 녹음 종료 | `recording_complete` | 200 + `COMPLETED` |
| 6 | 참여자별 수신 전사와 DB 조회 결과 대조 | `sse_transcript_verify`, `participants_complete` | 전사 ID·순번·본문·시간 일치, 참여자 전원 검증 성공 |
| 7 | 요약 완료 대기 | `summary_wait` (요청 `summary_poll`) | 제한 시간 안에 `COMPLETED` |
| 8 | 팀원 전원 전사·요약 조회 | `transcript_read`, `summary_read` | 예상 전사 건수 일치, 요약 완료·내용 있음 |

- `CREDENTIALS_FILE`의 계정으로 로그인하고 `FIXTURE_FILE`의 `preparation.teams`에서 회의 ID를 읽습니다. 첫 계정이 녹음 담당입니다.
- 오디오 파일은 공유 파일 핸들을 사용하며 녹음 VU만 송신 버퍼를 읽습니다. SSE 참여자 VU에는 파일 전체를 중복 적재하지 않습니다.
- 오디오는 `AUDIO_DURATION_MS` 동안 `CHUNK_INTERVAL_MS`(기본 20) 간격으로 보냅니다. `AUDIO_FORMAT`은 `webm_opus` 또는 `mp4_aac`입니다.
- `TRANSCRIPT_DRAIN_MS`(0~60000, 기본 5000)는 송신 후 전사 처리를 기다리는 시간입니다. WS 송신 실패·예외가 있어도 활성 녹음의 종료를 시도하며 `recording_cleanup`에 결과를 기록합니다. 정리에 실패했다면 서버 상태를 별도로 확인해야 합니다. 강제 프로세스 종료 시에는 정리 실행을 보장하지 않습니다.
- `EXPECTED_TRANSCRIPT_COUNT`는 종료 후 전사 총 건수이며 기본값은 `floor(AUDIO_DURATION_MS / 1000)`입니다. 현재 dummy의 초당 한 문장을 기준으로 하므로 실제 오디오 길이·공급자 동작이 다르면 명시적으로 지정합니다.
- `MIN_LIVE_TRANSCRIPTS`는 회의 중 최소 수신 건수이며 기본값은 `max(1, EXPECTED_TRANSCRIPT_COUNT - 5)`입니다. 중간 순번 누락·중복은 실패입니다. BE가 완료 시 SSE를 먼저 닫으므로 AI가 종료 후 확정하는 마지막 전사를 SSE에서 반드시 받는다고 가정하지 않습니다. STT 지연이 달라지면 drain 시간과 최소 건수를 함께 검토합니다.
- `SSE_READY_SECONDS`(1~300, 기본 60)는 팀원 준비 상한입니다. SSE timeout은 준비 상한 + 녹음 시간 + drain + 120초입니다. 시작 실패로 종료 이벤트가 발생하지 않으면 참여자는 이 상한에 종료됩니다.
- `SUMMARY_WAIT_SECONDS`(기본 1800), `SUMMARY_POLL_SECONDS`(기본 5)는 요약 대기 상한과 간격입니다. 요약 대기 중 등록 전 404는 기본 HTTP 실패율에서 제외하지만 요약 완료 실패는 별도 기록합니다.
- 추가 지표: `meety_flow_success`(팀 전체 흐름 성공률), `meety_transcript_sse_events`(참여자별 수신 합계), `meety_sse_held_ms`(SSE 유지 시간), `meety_summary_ready_ms`, `meety_meeting_duration_ms`. `meety_success_rate`는 `operation`별로 봅니다.
- 로컬 조율 HTTP 요청은 `operation=coordination`입니다. 전체 `http_reqs`·응답 시간에는 이 요청도 들어가므로 대상 앱의 단계별 태그로 분리해 분석합니다. VU 수는 실제 연결 수가 아니며 서버의 WS·SSE 활성 연결 수도 함께 측정합니다.
- 결과 조회는 팀별 요약 완료 후 실행되어 팀 간에 분산됩니다. 100팀 실행을 600명 동시 조회 시험으로 해석하지 않습니다. 조회 폭주 측정은 기존 단독 API 시나리오로 별도 실행합니다.
- S3 업로드·화자 분리는 범위 밖입니다. 로그에는 계정·토큰·전사 본문을 남기지 않습니다.

### `common.js`

k6의 공통 설정 파일로, 직접 실행하지 않습니다. `BASE_URL`, `ALLOW_LIVE_TEST=YES`, `FIXTURE_FILE`, `COUNT`를 검사합니다. `meeting-flow.js`는 fixture 형식이 달라 `BASE_URL`·`ALLOW_LIVE_TEST` 검사(`loadBaseUrl`)와 결과 집계만 함께 씁니다. `COUNT`를 생략하면 기존 `LEVEL=smoke|target|max`의 고정 수를 사용합니다.

### `prepare-local-auth.py` / `load_test_prep.py`

기존 계정 fixture를 로그인하거나 선택적으로 가입시키는 **별도 준비 방식**입니다. 이번 자동 생성 흐름에서는 실행할 필요가 없습니다. 특히 `load_test_prep.py --prepare-resources` 방식은 입력 팀 수가 20개로 제한되어 있어 50·100팀 단계에는 맞지 않습니다.

### `audio-ws.js` / `sse.js`

각각 녹음 WebSocket과 회의 이벤트 연결만 따로 측정합니다. **단독 스크립트는 6단계와 별도로 실행합니다.** 통합 흐름의 WS 송신과 참여자 SSE 수신은 `meeting-flow.js`가 함께 수행합니다. `sse.js` 실행에는 `k6/x/sse` 확장이 필요합니다.

회원·팀·fixture 준비 작업은 k6 측정 구간 밖에서 순차 실행됩니다. 동시 부하 결과는 3·5·6단계의 **회의 생성, 회의 참여, 회의 진행 각각**에 대한 k6 HTML 보고서뿐입니다.
